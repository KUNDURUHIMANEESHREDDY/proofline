# GitHub Actions evidence ingestion

Proofline accepts CI verification records through a Forge web trigger. Forge web trigger URLs are public endpoints and Forge does not authenticate callers; the handler therefore requires a per-installation HMAC secret, a fresh timestamp, and a one-time nonce.

## Trust model

- The signing secret is generated by a Jira administrator with the ADMINISTER global permission in the Proofline issue panel and stored using Forge KVS Secret Store.
- Copy the secret once into the GitHub repository's Actions secret named `PROOFLINE_WEBHOOK_SECRET`.
- Store the Forge web trigger URL in the repository Actions variable `PROOFLINE_WEBTRIGGER_URL`.
- The workflow signs the exact serialized JSON body using HMAC-SHA256 over `timestamp.nonce.body`.
- The handler allows a five-minute clock skew, claims the nonce before writing evidence, and rejects conflicting reuse of an evidence ID. Exact retransmissions of an already-accepted record are idempotent and do not increment the verdict summary again. Static response outputs intentionally return generic error bodies rather than detailed validation internals. Nonces expire after ten minutes. The submitter retries optimistic-concurrency contention (HTTP 503) with a fresh nonce.
- Secret rotation keeps the previous secret valid for 15 minutes so the GitHub Actions secret can be updated without an immediate outage.
- This authenticates possession of the shared secret. It is not a GitHub cryptographic workflow attestation. Protect the GitHub secret, restrict who can edit workflows, and only call the submit script from trusted workflows.
- A caller with the secret can submit any allowed issue key, criterion, and outcome for this Forge installation. Restrict the secret to trusted repositories/workflows and do not expose it to fork pull requests or untrusted code.
- Evidence and the strongly-consistent per-issue verdict summary are committed atomically. The trigger uses configured static response outputs, so it can return the required HTTP status codes without a dynamic response. Static web triggers are compatible with Runs on Atlassian eligibility; verify the complete app with `forge eligibility` after deployment.

## Setup

1. Install and authenticate the Forge CLI, then register this existing app with `forge register proofline`.
2. Run `forge lint`, then deploy with `forge deploy --environment development`.
3. Install the deployed app into a Jira Cloud site with `forge install --site <your-site>.atlassian.net --product jira --environment development`. Prefer a dedicated test site. If testing on a production site, use a dedicated throwaway test issue and treat its data as production data.
4. In that Jira issue, open the Proofline panel as a Jira administrator with the ADMINISTER global permission and choose **Create signing secret** (or **Rotate signing secret**). Copy the value immediately; it is shown only once.
5. Generate the installation-specific web trigger URL with `forge webtrigger create --functionKey github-actions-evidence --site <your-site>.atlassian.net --product Jira --environment development`.
6. Add repository Actions secret `PROOFLINE_WEBHOOK_SECRET` and Actions variable `PROOFLINE_WEBTRIGGER_URL`.
7. Run the **Proofline evidence verification** workflow manually from the Actions tab. Supply the Jira issue key and a criterion key that is configured on that issue. The workflow runs `npm ci` and `npm test`, then submits `PASS` or `FAIL` evidence to Forge.
8. Refresh the issue's Proofline panel and verify the evidence ID, source run ID, criterion, and derived verdict.

## Example workflow job

The verification job is responsible for running checks. The evidence job runs even when verification fails so a failure is not silently omitted. Adapt the criterion key to the check being reported.

```yaml
jobs:
  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
      - run: npm ci
      - run: npm test

  report-unit-tests:
    needs: unit-tests
    if: always() && needs.unit-tests.result != 'cancelled'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Submit evidence to Proofline
        env:
          PROOFLINE_WEBTRIGGER_URL: ${{ vars.PROOFLINE_WEBTRIGGER_URL }}
          PROOFLINE_WEBHOOK_SECRET: ${{ secrets.PROOFLINE_WEBHOOK_SECRET }}
          PROOFLINE_ISSUE_KEY: PAY-142
          PROOFLINE_CRITERION_KEY: unit-tests
          PROOFLINE_OUTCOME: ${{ needs.unit-tests.result == 'success' && 'PASS' || 'FAIL' }}
          GITHUB_RUN_ID: ${{ github.run_id }}
        run: node scripts/submit-proofline-evidence.mjs
```

The dedicated `proofline-evidence.yml` workflow uses `workflow_dispatch` so a test issue and criterion are selected explicitly. Keep the signing secret restricted to trusted workflows; do not expose it to pull requests from forks.

## Request format

Required headers:

- `X-Proofline-Timestamp`: Unix time in seconds.
- `X-Proofline-Nonce`: unique random identifier for this delivery.
- `X-Proofline-Signature`: `sha256=<hex HMAC>`.

The body must be a single v1 `verification` envelope from `github-actions`. Unknown fields, duplicate JSON keys, malformed timestamps, non-HTTPS artifact URIs, oversized bodies, and unsupported outcomes are rejected. The request body is limited to 64 KiB.

## Local submitter

Set the environment variables documented above and run:

```sh
node scripts/submit-proofline-evidence.mjs
```

The script uses only Node.js built-ins. It never prints the signing secret.
