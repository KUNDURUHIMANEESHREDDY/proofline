# GitHub Actions evidence ingestion

Proofline accepts CI verification records through a Forge web trigger. Forge web trigger URLs are public endpoints and Forge does not authenticate callers; the handler therefore requires a per-installation HMAC secret, a fresh timestamp, and a one-time nonce.

## Trust model

- The signing secret is generated by a Jira administrator with the ADMINISTER global permission in the Proofline issue panel and stored using Forge KVS Secret Store.
- Copy the secret once into the GitHub repository's Actions secret named `PROOFLINE_WEBHOOK_SECRET`.
- Store the Forge web trigger URL in the repository Actions variable `PROOFLINE_WEBTRIGGER_URL`.
- The workflow signs the exact serialized JSON body using HMAC-SHA256 over `timestamp.nonce.body`.
- The handler allows a five-minute clock skew, claims the nonce before writing evidence, and rejects duplicate evidence IDs. Nonces expire after ten minutes. The submitter retries optimistic-concurrency contention (HTTP 503) with a fresh nonce.
- Secret rotation keeps the previous secret valid for 15 minutes so the GitHub Actions secret can be updated without an immediate outage.
- This authenticates possession of the shared secret. It is not a GitHub cryptographic workflow attestation. Protect the GitHub secret, restrict who can edit workflows, and only call the submit script from trusted workflows.
- A caller with the secret can submit any allowed issue key, criterion, and outcome for this Forge installation. Restrict the secret to trusted repositories/workflows and do not expose it to fork pull requests or untrusted code.
- Evidence and the strongly-consistent per-issue verdict summary are committed atomically. The trigger uses Forge's `dynamic` response mode so it can return accurate HTTP status codes. Atlassian documents only static web triggers as eligible for the Runs on Atlassian program; this implementation therefore does not currently meet that eligibility condition.

## Setup

1. Install and authenticate the Forge CLI (`npm install --global @forge/cli`, then `forge login`).
2. Register this existing repository as a Forge app with `forge register proofline` (the command writes the Atlassian app ID into `manifest.yml`).
3. Run `forge lint`, then deploy with `forge deploy --environment development`.
4. Install the deployed app into a development Jira site with `forge install --site <your-site>.atlassian.net --product jira --environment development`.
5. In a Jira issue, open the Proofline panel as a Jira administrator with the ADMINISTER global permission and choose **Create signing secret** (or **Rotate signing secret**). Copy the value immediately.
6. Generate the web trigger URL with `forge webtrigger create --functionKey github-actions-evidence` and select the Jira installation/environment.
7. Add repository Actions secret `PROOFLINE_WEBHOOK_SECRET` and Actions variable `PROOFLINE_WEBTRIGGER_URL`.
8. Copy `scripts/submit-proofline-evidence.mjs` into the trusted CI repository (or make it available in that workflow), then add the example evidence job and set `PROOFLINE_ISSUE_KEY` and `PROOFLINE_CRITERION_KEY`.

## Example workflow job

The verification job is responsible for running checks. The evidence job runs even when verification fails so a failure is not silently omitted. Adapt the `needs` job and criterion key to the check being reported.

```yaml
jobs:
  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test

  report-unit-tests:
    needs: unit-tests
    if: always() && needs.unit-tests.result != 'cancelled'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Submit evidence to Proofline
        env:
          PROOFLINE_WEBTRIGGER_URL: ${{ vars.PROOFLINE_WEBTRIGGER_URL }}
          PROOFLINE_WEBHOOK_SECRET: ${{ secrets.PROOFLINE_WEBHOOK_SECRET }}
          PROOFLINE_ISSUE_KEY: PAY-142
          PROOFLINE_CRITERION_KEY: unit-tests
          PROOFLINE_OUTCOME: ${{ needs.unit-tests.result == 'success' && 'PASS' || 'FAIL' }}
          PROOFLINE_SUMMARY: Unit test job result from GitHub Actions
          GITHUB_RUN_ID: ${{ github.run_id }}
        run: node scripts/submit-proofline-evidence.mjs
```

The sample workflow must be copied into the CI repository that has access to the Proofline secret and the submit script. Do not make the secret available to pull requests from forks.

## Request format

Required headers:

- `X-Proofline-Timestamp`: Unix time in seconds.
- `X-Proofline-Nonce`: unique random identifier for this delivery.
- `X-Proofline-Signature`: `sha256=<hex HMAC>`.

The body must be a single v1 `verification` envelope from `github-actions`. Unknown fields, duplicate JSON keys, malformed timestamps, non-HTTPS artifact URIs, oversized bodies, and unsupported outcomes are rejected. The request body is limited to 64 KiB.

## Local submitter

Set the environment variables documented above and run:

```sh
node scripts/submit-proofline-evidence.mjs
```

The script uses only Node.js built-ins. It never prints the signing secret.
